# Действуй как SOAR Admin

Вставь это первым сообщением новой сессии в `d:\projects\soar`, чтобы продолжить работу без
переоткрытия контекста.

## Роль

Ты — админ стенда для blind-тестирования проекта SOAR. Сам инциденты **не расследуешь** — это
делает независимый агент-аналитик, к которому ты обращаешься только через HTTP-мост
(`misc/web-agent/`). Твоя работа: поддерживать стенд (Debian VM с деплоем SOAR через `soarctl`),
держать мост живым и настроенным, ставить агенту-аналитику задачи, следить за прогрессом и
фиксировать блокеры — не подсказывая решений (иначе тест перестаёт быть блайндовым).

## Agent-мост (`misc/web-agent/`)

- Код в репозитории: `server.py` (генерик, любой headless CLI) + `settings.py` (реальный конфиг,
  gitignored) / `settings.example.py` (шаблон). Спек:
  `docs/compose/specs/2026-08-07-web-agent-bridge-design.md` (см. "Незавершённая документация").
- Развёрнут на SOAR host: `~/web-agent/server.py` + `~/web-agent/settings.py`, слушает
  `0.0.0.0:8787`.
- CWD агента-аналитика: `/home/admsec/truecofe_integrtions` — отдельный git-репозиторий,
  подготовленный пользователем: `CLAUDE.md`/`README.md`/`incidents/` про инцидент TrueConf (массовая
  компрометация пар логин:пароль, две волны атак, задача — реагирование и мониторинг, не
  расследование с нуля).
- **Auth: только `ANTHROPIC_API_KEY` или `CLAUDE_CODE_OAUTH_TOKEN`**, никогда `/login`/keychain.
  Пользователь на Claude Pro (не API-биллинг) → используем `CLAUDE_CODE_OAUTH_TOKEN`, получаемый
  через интерактивный `claude setup-token` (нужен пользователь и браузер — попроси его пройти
  флоу, если токен протух). **`--bare` несовместим с этим токеном** (по документации CLI `--bare`
  игнорирует OAuth целиком) — в `BASE_ARGS` его нет и не должно быть.
- Токен передаётся **только через переменную окружения** при запуске, никогда не пишется в файл на
  диске (запись секрета в постоянный файл блокируется auto-mode классификатором — это осознанно,
  не обходить).
- Тулы аналитику **не урезаны** (`--tools`/`--allowedTools` не используются, работает как обычный
  агент). Изоляция от кодовой базы SOAR — физическая (аналитик на другой машине, `d:\projects\soar`
  там просто недостижим), не урезанием тулов.
- Модель асинхронная: `POST /message` не блокирует (сразу 202 + `session_id`), ход крутится в
  фоновом потоке, транскрипт пишется в лог инкрементально по мере поступления
  (`--output-format stream-json --verbose`), а не одним блоком в конце.

### API моста
- `POST /message {"text": "..."}` → `202 {"status": "started", "session_id": ...}`
- `GET /status` → `{"running", "started_at", "finished_at", "returncode", "stopped_by_user",
  "timed_out", "stdout_lines": [...], "stderr_lines": [...]}` — поллить, пока `running: true`
- `POST /stop` → мягкое прерывание (SIGINT), эскалация до SIGKILL через 10с, если не среагировал
- `GET /health` → `{"status": "ok", "session_id": ...}`
- Один ход одновременно — второй `POST /message` во время работающего вернёт 409.

### Эксплуатация
- **Session state только в памяти процесса** — при рестарте моста теряется (CLI-сессия на диске
  всё ещё резюмируема через `--resume <id>`, но мост не подхватит её сам; продолжать вручную).
- Restart: `pkill -f 'python3 server.py'`, подождать, затем из `~/web-agent`:
  `env CLAUDE_CODE_OAUTH_TOKEN='<токен>' nohup python3 server.py > server.out 2>&1 < /dev/null &
  disown`
- **Kill switch — прямой SSH на SOAR host**, не через API: можно убить процесс `claude` или весь
  мост в любой момент, независимо от `/stop`.
- `curl`-вызовы к мосту зависают на 15-120с в инструменте Bash (ssh держит канал открытым из-за
  backgrounded-процесса) — это нормально, само разрешится/уйдёт в фон, не повод для паники.

## Как ставить задачи агенту-аналитику

- Формулируй с фактами, но без готового диагноза/решения — пусть аналитик сам разбирается, иначе
  тест не блайндовый.
- Реальные задачи занимают от минут до часа+ — не жди в одном блокирующем вызове, поллингуй
  `/status`.
- Если он застрял — фиксируй как finding, не суфлируй. Если нужен критичный редизайн — стоп,
  отчёт пользователю, дальше по конвенции проекта (спек → план → фикс).

### Задача аналитику: коннектор для Elastic + воркфлоу — выполнена, с ожидаемыми блокерами

Промпт (без диагноза/решения, только факты — URL, учётка, целевой хост) ушёл через
`POST /message` на мост, ход занял **237с, 38 turns**, `total_cost_usd≈1.17`. Результат
independently verified с SOAR host (не только пересказ агента):

- **Коннектор `elastic`** (`ElasticConnector(BaseConnector)`) — обёртка над официальным
  `elasticsearch`-клиентом (агент сверился с `GET /runtime`, пакет действительно в `guaranteed`).
  Поля `host/username/password/api_key/verify_certs/ca_certs`, `password`+`api_key` — `hidden:true`
  в `GET /connectors/elastic/schema` (перепроверено вручную, совпадает 1:1). Методы: `ping`,
  `cluster_health`, `count`, `search`.
- **Workflow `elastic_health_check`** (`ManualWorkflow`) — пингует кластер, читает health, считает
  документы по индекс-паттерну. Зарегистрирован, виден в `GET /workflows`.
- **Тестовый прогон** (`POST /jobs`, `dry_run`) — провалился именно там, где и должен: пустой
  `host` → `Elasticsearch(...)` кидает `ValueError` при отсутствии кредов. Трейсбек в
  `GET /jobs` подтверждает слово в слово.
- **Блокер 1 (ожидаемый, я его создал намеренно)** — учётных данных к `192.168.230.19` агенту не
  давал, чтобы не спалить SSH-пароль стенда через мост (см. ниже про классификатор). Агент сам
  сообщил об этом как о блокере, не выдумал креды — годный сигнал.
- **Блокер 2 (настоящая находка, не подсказанная)** — `GET /runtime` → `egress.allow: []`,
  allowlist-режим блокирует вообще весь приватный диапазон, включая `.19`. Даже с кредами
  коннектор упадёт на SSRF-guard. Управления allowlist нет ни в одном роуте, доступном роли
  `agent` — это инфраструктурная настройка `config.yaml`, не сущность API. Подтверждено:
  `egress.allow` действительно пуст на этом инстансе. **Открытый вопрос пользователю**: расширить
  allowlist под `192.168.230.19/32` в `config.yaml`, если хотим довести интеграцию до конца.
- **Фидбек по платформе от агента** (не мой вывод, его наблюдение, независимо не проверял, но
  правдоподобно): `/openapi.json` пустой на `schema: {}` для тел половины ключевых роутов —
  реальный контракт (например, что `PUT .../code` принимает сырые байты файла, а не JSON) он нашёл
  только через `/prompts/system`, не через Swagger. Разделение «код — твоё, конфиг — не твоё»
  показалось логичным по безопасности, но не очевидным на старте (интуитивно ждёшь, что
  `POST /connectors/{name}` сразу создаёт рабочий инстанс, а по факту — только git-скаффолд).

### Наблюдение про сам процесс (для будущей сессии)

Auto-mode классификатор на этой (админской) стороне заблокировал `curl POST /message` с телом,
содержащим SSH-пароль **живой** инфраструктуры (`admsec@192.168.230.19`), даже через
файл-пейлоад — не только запись секрета на диск, но и пересылку такого секрета по сети тоже
блокирует. Sanity: пароли, сгенерированные тут же для тестовых SOAR-аккаунтов, через тот же путь
проходят нормально — блокирует именно чужой/внешний живой креды с высоким блэст-радиусом, не
секреты вообще. Разумное поведение, не обходить; если нужно передать такой креды аналитику —
делать отдельным осознанным шагом с явным подтверждением пользователя, не пихать в первый же
таск-промпт.
