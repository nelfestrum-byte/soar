# CLAUDE.md — рабочие инструкции для этого проекта

Основной источник истины: **[AGENTS.md](AGENTS.md)** — читай его первым делом в любой сессии.

## Что это за проект

Минималистичный SOAR без LLM. Детерминированные автоматические расследования на ECS-схеме, автоматическое закрытие стандартных кейсов с FP.

Два компонента:
- `soar/` — коннекторы, actions, workflows (Python-пакет)
- `orchestrator/` — FastAPI оркестратор (очередь, воркеры, планировщик, git-версионирование)

`ui/` — стенд для ручного тестирования; дорабатывается до продакшен-уровня
юзабельности (точки контроля, видимость логов и аудита), но остаётся вне
основного продукта — фичи оркестратора не блокируются на его состоянии.

## Модель сущностей — это суть проекта, а не деталь реализации

Четыре сущности (коннектор, экшен, инструмент, рабочий поток) и три принципа
их разделения — нормативный раздел **[AGENTS.md#модель-сущностей](AGENTS.md)**.
Объяснение, карта дрейфа и план возврата —
**[`docs/concepts/ENTITY-MODEL.md`](docs/concepts/ENTITY-MODEL.md)**.

Коротко, чтобы держать в голове в любой задаче:

1. **Проект даёт гарантии, контент их получает.** Тела коннекторов — контент
   (может стать чужим, уехать в контентпак). Контракт, реестры, схема
   конфига — проект. Контракт не уезжает в контент никогда.
2. **Прозрачность обеспечивает платформа, а не дисциплина автора.**
   Логирование, аудит, dry-run, редакция секретов — на границе, где платформа
   отдаёт сущность потоку. Не внутри кода сущности.
3. **Одна сущность — одно место жительства.** Один источник исполнения.
   Никаких «копия в пакете и копия в данных».
4. **Проект объясняет себя через API.** Пишущий код — человек или
   LLM-агент — узнаёт всё из API, не читая исходники и не имея доступа к
   хосту. Включая окружение исполнения: что доступно для импорта и что из
   этого гарантировано. Зависимости запекаются в образ как версионированный
   контракт; установки пакетов в рантайме нет (air-gap + эфемерность
   контейнера).
5. **Рантайм контента отделён от рантайма платформы.** У контента свой venv;
   внутренности платформы недоступны физически, а не по договорённости.
   Граница зависимостей, не песочница. Наблюдаемость — два уровня: прокси
   на реестре (намерение) и аудит-хук `sys.addaudithook` (факт); прокси
   границей безопасности не является.

Эти правила старше любой задачи. Задача, которая их нарушает, решается
неправильно, даже если тесты зелёные — все найденные 2026-07-29 дефекты
(правка коннектора через API молча не применяется, зависимости 11 из 24
коннекторов не ставятся, обновления контента не доезжают) возникли именно
из-за того, что модель нигде не была записана. Если задача требует нарушить
принцип — сначала правка `ENTITY-MODEL.md` и агентских файлов, потом спек,
потом код. Не наоборот.

## Обязательный порядок работы

**Перед написанием кода — написать спек.** Всегда.

```
docs/compose/specs/YYYY-MM-DD-<feature>-design.md   ← сначала
docs/compose/plans/YYYY-MM-DD-<feature>.md           ← потом
docs/compose/reports/<feature>.md                    ← после завершения
```

Формат спеков — как в существующих примерах: `[S1] Problem`, `[S2] Solution`, ...
Формат планов — checkbox-и `- [ ]`, test-first (сначала падающий тест).

## Что читать, что не читать

**Читать:** `soar/`, `orchestrator/`, `tests/`
**Читать по задаче:** `ui/` — при работе над UI-фичами (см.
`docs/compose/specs/2026-07-29-ui-control-visibility-design.md`); тесты —
vitest, `cd ui && npm test`
**Не читать:** `deploy/` — вспомогательное

При поиске по кодовой базе — использовать Grep/Glob, не читать файлы целиком без причины.

## Ключевые паттерны (детали — в AGENTS.md)

- **Workflow lifecycle:** `JobManager.enqueue()` → `Worker._execute()` → `SubprocessRunner` → `soar.runner` subprocess
- **Workflow key:** имя файла без `.py` (не имя класса) — `WorkflowRegistry` использует `module_name` как ключ
- **Connector lazy init:** `_ensure_connected()` при первом вызове метода
- **Git auto-commit:** любое изменение файла через API коммитится через `GitManager`
- **Auth:** JWT+RBAC с v0.5.1, но опционален — `auth.secret_key = ""` в config → анонимный admin (Docker-сетевое доверие); на deploy/stage включена с v0.9
- **Dry-run:** `context["dry_run"] = True` в `POST /jobs` → workflow пропускает мутации

## Чего не делать

- Не рефакторить вне задачи — только минимальный фикс/фича
- Не писать комментарии, объясняющие что делает код — только WHY если неочевидно
- Не обращаться к `_metas`, `_redis`, `_ensure_connected()` из API роутов — только публичные методы
- Не импортировать `load_workflow_metas` из `orchestrator.main` — вынести в `core/` при следующем рефакторе
- Не обновлять AGENTS.md заранее — только после выполнения задачи

Нарушения модели сущностей (см. раздел выше) — отдельно, это не стилистика:

- **Не класть контент в пакет `soar/`** — ни коннектор, ни экшен, ни воркфлоу.
  Их место в `connectors_dir`/`actions_dir`/`workflows_dir`. `soar/connectors/`
  с 24 каталогами — известное нарушение (трек 3), не образец для подражания
- **Не класть в `soar/tools/` то, что не предназначено рабочему потоку.**
  Универсальности мало — нужна обращённость к потоку. Внутренняя механика
  оркестратора идёт в `orchestrator/core/`, приватные хелперы — в `_*.py`
- **Не реализовывать гарантию внутри кода сущности.** Лог, аудит, dry-run,
  редакция секретов — на границе (реестр/прокси), а не «попросим авторов
  коннекторов пользоваться `http_client`». Для контента просить некого
- **Не заводить второй источник исполнения одной сущности** — ни копией в
  пакете, ни fallback-путём, ни «на всякий случай прочитаем ещё и оттуда»
