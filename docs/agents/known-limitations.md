# Known Limitations

Полные описания + workaround. Краткий список названий — в [AGENTS.md](../../AGENTS.md).

| # | Limitation | Workaround until fixed |
|---|------------|------------------------|
| 1 | **ConcurrencyPolicy.QUEUE** — реализован в Worker как busy-wait: ждущий job занимает воркер целиком; между проверкой "нет RUNNING" и установкой RUNNING есть гонка — два QUEUE-job могут стартовать одновременно | Не полагаться на строгую сериализацию; для критичных workflows использовать FORBID |
| 2 | **RedisQueue may lose messages on connection drop** — at-most-once delivery, no ACK | Use `queue.backend: sql` (default in `deploy/prod` since v0.12) for critical workflows — polls `workflow_jobs`, no separate at-most-once broker; Redis remains available for high-throughput non-critical use |
| 3 | **Worker crash recovery работает только при `jobs.persistence: sql`** — на дефолте (`memory`) хранилище in-memory: на старте пустое, recovery фактически no-op | Установить `jobs.persistence: sql` (`database.url` на Postgres/SQLite-файл) для продакшна |
| 4 | **JobStore теряет историю при рестарте только на дефолте `jobs.persistence: memory`** — с `sql` история переживает `docker compose restart` (см. Database backend в `docs/agents/config-reference.md`) | Export jobs before restart if history matters (только для `memory`) |
| 5 | **`keep_completed` eviction** — eviction policy is FIFO by insertion order | Do not rely on old completed jobs being available if throughput is high |
| 6 | **`AuditLog.actor_name` для JWT-пользователей — числовой id, не логин** — JWT payload несёt только `{sub, role, type}`, без username (нет DB-lookup на каждый запрос по дизайну); только API-key (service) акторы несут читаемое имя (`CurrentUser.username = key.name`) | Смотреть `actor_id` и сверять с `/auth/keys` или БД `users`, если нужен логин, а не id |
| 7 | **`PATCH /auth/users/{id}` не защищает от деактивации/разжалования последнего admin'а** — self-lockout guard (409) есть только для собственного аккаунта; admin A может деактивировать или понизить в роли admin B, даже если B — единственный другой admin, оставив систему без работающих админов (кроме A). С v0.12+ (B1, `2026-07-28-auth-deactivation-revocation-design.md`) деактивация/смена роли B действительно отзывает все живые refresh-токены B в той же транзакции — B теряет доступ немедленно, а не только на следующий `/auth/login` | Принято как остаточный риск (см. `UPGRADE-v2.md` P15) — recovery вне API: `python -m orchestrator.auth.cli create-user --role admin` заводит нового admin'а независимо от текущего состояния пользователей |
| 8 | **Мультиинстансность вне scope деплой-тулинга (`soarctl`)** — `database.table_prefix` уже позволяет нескольким инстансам SOAR шарить одну физическую БД, но у CLI/деплой-тулинга нет понятия «контекста»/профиля нескольких одновременно управляемых инстансов; `soarctl` рассчитан на один инстанс за раз (см. `docs/compose/specs/2026-07-22-deploy-cli-design.md`) | Для нескольких инстансов — отдельные рабочие директории/чекауты с собственным `.env`/`config.yaml`, без общего CLI-контекста. Управление несколькими инстансами одним CLI требует отдельного дизайна |
| 9 | **Правка предустановленного коннектора через API не применяется** — коннектор существует и в пакете `soar/connectors/<name>/`, и копией в `connectors_dir` (сидинг `cp -rn` в Dockerfile); `ConnectorRegistry._discover_external()` пропускает модуль, уже загруженный из пакета (`if fqn in sys.modules: continue`), поэтому исполняется пакетная копия. Конфиг при этом читается из **обоих** каталогов и внешний побеждает: `PUT /connectors/{name}/config` применяется, `PUT /connectors/{name}/code` — нет, молча, с успешным ответом и git-коммитом. Касается только 24 встроенных коннекторов (E1 в [`ENTITY-MODEL.md`](../concepts/ENTITY-MODEL.md)) — структурный дубль сам по себе не устранён, это Фаза 3 (контентпак). **После Фазы 2** (`ConnectorProxy`, `docs/compose/reports/entity-model-in-code.md`) это уже не влияет на логирование/dry-run/аудит: какая бы копия ни исполнялась (пакетная или внешняя), доступ к ней всегда идёт через шим → `ConnectorProxy` — `SOAR_AUDIT_EVENT`/dry-run/редакция `HIDDEN_FIELDS` гарантированы независимо от того, какой код физически выполнился. Остаётся баг только в применении **правки кода**, не в наблюдаемости того, что уже выполняется | Правки кода встроенного коннектора вносить в `soar/connectors/<name>/` и передеплоить; для изменённого поведения — создать коннектор с новым именем, он попадёт только в `connectors_dir` и сработает штатно |
| 10 | ~~Зависимости 11 из 24 встроенных коннекторов не установлены в образ~~ — **закрыто**, см. ниже | — |

**Закрыто в v0.12:** бывший #7 (`GitManager.commit()` не распознавал "nothing to commit" при untracked-файлах, тихо терял audit-запись) — заменено детерминированной проверкой через `git diff --cached --quiet`, см. `docs/compose/reports/git-manager-nothing-to-commit.md`. Номер переиспользован для бывшего #8 (admin lockout), бывший #9 (мультиинстансность) стал #8 — внешние ссылки на старые номера обновлены.

**Закрыто в Runtime Boundary Phase 1 (E2, E9, E10.3 из `ENTITY-MODEL.md`):** бывший #10 (`soar/requirements.txt` не ставился ни одним Dockerfile — 11 из 24 встроенных коннекторов не хватало пакетов). `deploy/{prod,stage}/Dockerfile.orchestrator` теперь собирают два venv (`platform-venv` из `orchestrator/requirements.txt`, `content-venv` из `soar/requirements.txt`); `SubprocessRunner` запускает воркфлоу через `content-venv` (`SOAR_CONTENT_PYTHON`, fallback на `sys.executable` вне Docker). Заодно закрыты: **E9** (окружение исполнения не было описано по API — теперь `GET /runtime` отдаёт `soar/runtime_contract.py` + фактически установленные пакеты content-venv) и **E10.3** (`load_workflow_metas` импортировал пользовательский код воркфлоу в процессе оркестратора при каждом reload — заменено AST-парсингом, `orchestrator/core/introspect.py::parse_workflow_meta`). См. `docs/compose/reports/runtime-boundary.md`.
