## A. Находки

### F1. `requestBody` не задекларирован в OpenAPI для 5 write-эндпоинтов, принимающих сырые байты

`orchestrator/api/connectors.py:583` (`PUT /{name}/code`), аналогично
`POST /{name}` (589-е, создание), `PUT /{name}/config`; `orchestrator/api/workflows.py`
(`PUT /{name}/code`); `orchestrator/api/actions.py` (`PUT /{name}`).

Хендлеры принимают `request: Request` и читают тело вручную
(`await request.body()`), а не через Pydantic-модель — поэтому FastAPI не
может вывести схему, и `GET /openapi.json` отдаёт для этих пяти методов
**вообще без ключа `requestBody`**. Проверено на живом инстансе:

```
methods with no requestBody declared: 12
  ('PUT', '/workflows/{name}/code')
  ('PUT', '/actions/{name}')
  ('POST', '/connectors/{name}')
  ('PUT', '/connectors/{name}/code')
  ('PUT', '/connectors/{name}/config')
  ... (ещё 7 — /enable, /disable, /reload, /cancel, /webhooks — этим
       телo действительно не нужно, ложных срабатываний нет)
```

Разница между «телу не нужно» и «тело нужно, но не описано» проверена
вручную по каждому из 12 — реальный гэп только у пяти write-эндпоинтов
выше.

**Почему это не косметика, а нарушение принципа проекта.** `CLAUDE.md`,
пункт 4 модели сущностей: «Проект объясняет себя через API. Пишущий код —
человек или LLM-агент — узнаёт всё из API». Для этих пяти роутов это не
так — агент в этом заходе получил 422 на первой попытке (`{"content":
"..."}` вместо сырых байт), потратил ход на угадывание, и в итоге нашёл
реальный контракт не в Swagger, а в `GET /prompts/system` — недокументированный
для этой цели побочный канал, который не гарантирован и не выглядит как
источник контракта API.

**Фикс:** `openapi_extra` в `@router.put/post(...)` для всех пяти роутов —
явно указать `requestBody.content.text/plain` (или что там реально
ожидается) вместо оставлять пустым. Без изменения рантайм-поведения
(байты как принимались, так и будут). Кандидат на отдельный спек/план —
затрагивает 3 файла API, no schema/DB changes.

### F2. Пустой egress allowlist на свежем инстансе блокирует любую интеграцию с приватной целью — решение, не дефект

`GET /runtime` → `egress: {"mode": "allowlist", "allow": []}` — подтверждено
на этом инстансе. Работает по спеку
(`docs/compose/specs/2026-08-06-egress-policy-design.md`,
`docs/compose/reports/egress-policy.md`): allowlist — заведомо не
самообслуживаемый параметр, `agent` имеет только read через `GET /runtime`,
управление — правкой `config.yaml` на хосте. Агент упёрся в это ровно так,
как спроектировано, и корректно доложил находку вместо того чтобы обойти.

Практический эффект для этого стенда: коннектор `elastic` не заработает
даже после выдачи креды к `192.168.230.19` — allowlist пуст, TCP на этот
адрес блокируется до правки конфига руками.

**Не фикс, а решение заказчика:** если нужно довести интеграцию с
`192.168.230.19` до конца — добавить `192.168.230.19/32` в
`egress.allow` в `~/soar/deploy/prod/config.yaml` на хосте и
`docker compose restart orchestrator`. Если стенд останется чисто для
тестирования контракта (без реального сетевого похода к цели) — оставить
как есть, задокументировать как ограничение среды, не заводить тикет.

## B. Что подтверждено рабочим без замечаний

- **RBAC роли `agent`** — `PUT /connectors/{name}/code`, `POST
  /connectors/{name}`, `PUT /workflows/{name}/code`, `POST /jobs` доступны;
  `PUT /connectors/{name}/config` (секреты) — недоступен, ровно как задумано
  commit 857ecd2. Агент не пытался обойти через `/config/restore` (тоже
  закрыт на `admin` этим же commit).
- **Редакция секретов**: `GET /connectors/elastic/schema` → `password` и
  `api_key` — `hidden: true`, остальные поля — `false`. Перепроверено
  отдельным вызовом от лица `admin`, совпадает с тем, что репортил агент.
- **Реестр воркфлоу/коннекторов**: `GET /connectors`, `GET /workflows`
  показывают ровно то, что агент создал (`elastic` /
  `elastic_health_check`), без расхождений.
- **Диагностика падения job**: трейсбек в `GET /jobs` («empty host →
  `ValueError` at `Elasticsearch(...)` constructor») совпадает с тем, что
  агент описал в отчёте — контракт `execute()`/traceback propagation не
  теряет информацию (в отличие от бага a446e20, который чинили раньше).
- **`GET /runtime`**: `elasticsearch` пакет корректно в `guaranteed`
  (`kind: vendor`) — агент сверился с этим перед тем как писать
  `import elasticsearch`, а не гадал.

## Приложение Б. Организационное наблюдение

Auto-mode классификатор на моей (админской) стороне заблокировал попытку
переслать аналитику пароль SSH к живой инфраструктуре (`admsec@192.168.230.19`)
внутри тела `POST /message` — не только запись секрета на диск (уже было
известно из `misc/web-agent/soar-admin-session-prompt.md`), но и его
пересылку по сети тоже. Тестовые пароли, сгенерированные тут же для новых
SOAR-аккаунтов, прошли тем же путём без вопросов — блокируется конкретно
чужой/внешний креды с высоким блэст-радиусом, не секреты вообще. Из-за
этого задача аналитику ушла без SSH-доступа к цели — прямая причина, почему
F2 не был доведён до сетевой проверки в этом заходе (см. рекомендацию 3).
