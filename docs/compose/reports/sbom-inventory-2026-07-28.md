# SBOM-инвентаризация проекта SOAR — 2026-07-28

## Методология

- Прямые зависимости взяты из манифестов: `soar/requirements.txt`, `orchestrator/requirements.txt`, `ui/package.json`, `deploy/*/Dockerfile*`.
- Lock-файлов для Python в проекте нет (только диапазоны версий `>=`), поэтому дерево транзитивных зависимостей зафиксировано **эмпирически**: собран временный venv (Python 3.12.5), в него установлены оба requirements.txt одновременно, зафиксирован `pip freeze`.
- Лицензии Python-пакетов — через `pip-licenses` (metadata PyPI-пакетов, установленных в venv).
- Известные CVE в резолвленных версиях — через `pip-audit` (сверка с PyPA Advisory DB, требует интернет; выполнено успешно).
- Для `ui/` `node_modules` уже был установлен в репозитории (`npm ci` не потребовался) — лицензии извлечены напрямую из `package.json` каждого пакета.
- Docker base images и OS-уровень (apt/apk) — по содержимому Dockerfile, без построения образов и без `syft`/`trivy` (не устанавливались — не согласовывалось с пользователем; при необходимости точного OS SBOM это отдельный шаг).

Артефакты (снимки, не хранить в репо как источник истины — дерево пересчитывается заново при каждой сборке из-за отсутствия лока):
`pip-freeze.txt`, `pip-licenses.json`, `pip-audit.json`, `npm-licenses.json` — временные, в scratchpad сессии.

### CVE (pip-audit, PyPA Advisory DB)

Найдена **1 непропатченная уязвимость**:

- **`ecdsa==0.19.2`** — `PYSEC-2026-1325` / `CVE-2024-23342` / `GHSA-wj6h-64fc-37mp`. Timing-атака Minerva на кривую P-256 через `ecdsa.SigningKey.sign_digest()` — может привести к раскрытию приватного ключа при возможности точных замеров времени. **Фикса нет** — апстрим считает side-channel атаки вне скоупа проекта.
  - `ecdsa` — транзитивная зависимость `python-jose[cryptography]` / `paramiko`.
  - Проверено: JWT в `orchestrator/config.py:12` по умолчанию `algorithm: str = "HS256"` (HMAC, не ECDSA) — при дефолтной конфигурации `ecdsa`-путь для подписи токенов не используется. Риск актуален только если включат ES256/ES384 для JWT или если атакующий имеет возможность side-channel замеров на SSH-хосте (paramiko + ECDSA host/client keys).

Остальные 83 пакета — известных уязвимостей в резолвленных версиях не найдено.

### Несовпадение декларируемых и реально поставляемых зависимостей

`deploy/stage/Dockerfile.orchestrator` и `deploy/prod/Dockerfile.orchestrator` ставят:

```
pip install -r orchestrator/requirements.txt elasticsearch vt-py requests httpx
```

— то есть **не весь** `soar/requirements.txt`. В образ **не попадают**: `paramiko`, `ldap3`, `pymysql`, `pymssql`, `aiogram`, `aiosmtplib`, `pywinrm`, `smbprotocol`, `shodan`, `pymisp`, `psycopg2-binary`.

Коннекторы, которые их используют (`ssh`, `active_directory`, `smb_rpc`, `telegram`, `smtp` и др. — см. `soar/connectors/`), при реальном деплое через эти Dockerfile получат `ImportError` при первом вызове (`_ensure_connected()`), несмотря на то, что формально числятся зависимостью проекта. Это не баг SBOM-инвентаризации, а факт: **SBOM самого репозитория и SBOM реально поставляемого prod/stage-образа — разные множества**. Для передачи третьей стороне нужно явно решить, какой набор коннекторов входит в пилот, и синхронизировать Dockerfile.

# Риски передачи проекта другой компании (пилот SOC)

Контекст: сейчас — внутренний продукт без формальной лицензии. Ниже — риски именно в разрезе SBOM/зависимостей и юридического статуса кода, не общие риски пилота.

1. **Отсутствие LICENSE = «все права защищены» по умолчанию.** Без явного лицензионного документа у принимающей компании нет легального основания использовать, модифицировать или запускать код — даже в рамках пилота, даже бесплатно. Это главный риск: технически можно передать архив/репозиторий, но юридически это не даёт получателю прав. **Нужно оформить письменный pilot/NDA-agreement с явным (пусть и ограниченным, отзываемым) грантом на использование**, иначе сам факт передачи не создаёт правовой определённости ни для одной из сторон.

2. **Compliance по LGPL/MPL-зависимостям при дистрибуции.** В дереве зависимостей — `paramiko` (LGPL-2.1), `ldap3` (LGPLv3), `psycopg2-binary` (LGPL), `pymssql` (LGPL), `certifi` (MPL-2.0). Для внутреннего использования (SaaS/self-host в своей же инфраструктуре) LGPL/MPL не требуют раскрытия исходников продукта. Но при **дистрибуции** третьей стороне (даже пилотной) типично требуется: (а) сохранить copyright/license notices этих библиотек, (б) обеспечить получателю возможность заменить/обновить LGPL-библиотеку (выполняется автоматически, т.к. это отдельные pip-пакеты, не форкнутые/не завендоренные в код). На практике риск невысокий (это стандартные PyPI-зависимости без модификаций), но формально перед передачей стоит приложить NOTICE-файл со списком лицензий (можно сгенерировать из `pip-licenses.json` этого отчёта) — иначе формальное нарушение LGPL/MPL при дистрибуции. GPL (сильный copyleft, требующий раскрытия исходного кода SOAR целиком) в дереве **не обнаружен** — это снимает наиболее острый юридический риск.

3. **Раскрытие детекторной логики / IP.** Workflows и правила детектирования (`soar/workflows/`) — это конкурентное преимущество/детали внутренних процессов SOC-заказчика продукта. Передача полного репозитория раскрывает не только платформенный код, но и бизнес-логику расследований (какие IOC, какие пороги, какая логика авто-закрытия FP). Стоит решить: передаётся ли весь репозиторий или платформа без специфичных workflow/правил.

4. **Дрейф версий без lock-файла.** `requirements.txt` использует `>=`, лока нет. Если принимающая компания соберёт образ у себя через полгода, резолвятся другие (более новые) версии транзитивных зависимостей, чем протестированные здесь — воспроизводимость сборки не гарантирована, SBOM «поплывёт» без вашего контроля. Перед передачей стоит зафиксировать версии (`pip freeze` в лок/constraints-файл или `pip-tools`/`poetry`) — это также прямое требование большинства SOC security-intake процессов (they will ask for a pinned SBOM, not ranges).

5. **Несинхронизированный prod/stage Docker-образ.** Реально поставляемый в контейнере набор пакетов уже сейчас уже, чем заявлено в `soar/requirements.txt` (см. §4 выше) — часть коннекторов не будет работать «из коробки» у получателя. Если это не осознанное решение, стоит явно определить пилотный scope коннекторов до передачи, иначе при первом запуске у другой компании всплывут `ImportError`, что выглядит как баг с их стороны, хотя это осознанный (или случайный) пробел в Dockerfile.

6. **Единственная непропатченная уязвимость (`ecdsa` / CVE-2024-23342).** Низкий практический риск при дефолтном HS256 для JWT, но при передаче стороннему SOC на security-review это будет обязательно найдено их сканером (Dependabot/Snyk/pip-audit) в первый же день — стоит заранее задокументировать это как «known accepted risk, no upstream fix» в передаваемых материалах, а не давать им обнаружить это самостоятельно и делать выводы о качестве security-процессов.

7. **Захардкоженный stage-секрет в истории git.** `deploy/stage/config.yaml` содержит секрет для подписи JWT прямо в репозитории. При передаче репозитория с полной историей — секрет уходит вместе с кодом. Нужно либо исключить `deploy/stage/` из передаваемого среза, либо сгенерировать новый секрет перед передачей (сам факт, что он предназначен только для внутреннего stage, не отменяет того, что он станет публично известен третьей стороне).

8. **Отсутствие явного disclaimer об ответственности.** Продукт — «минималистичный SOAR без LLM» с автоматическим закрытием кейсов с FP на детерминированной логике. Если пилот SOC будет полагаться на него в реальном IR-процессе без письменного «AS IS, без гарантий, pilot only» — при сбое автоматизации (например, ложное авто-закрытие реального инцидента) неясная договорная база создаёт риск претензий уже не по лицензии, а по качеству/полноте функциональности. Это не SBOM-риск сам по себе, но прямое следствие того, что «лицензии нет» — нет и стандартного warranty disclaimer, который обычно идёт в её тексте (MIT/Apache и т.п. содержат явный "AS IS" пункт).

## Рекомендации перед передачей (кратко)

- Оформить письменный pilot-agreement с явным грантом прав + AS-IS disclaimer — закрывает риски 1 и 8.
- Сгенерировать и приложить NOTICE-файл лицензий сторонних зависимостей (готовая основа — `pip-licenses.json` из этого прогона) — закрывает риск 2.
- Решить и зафиксировать scope: полный репозиторий или платформа без специфичных workflows/правил — риск 3.
- Запинить зависимости (lock/constraints) перед сборкой образа для передачи — риск 4.
- Синхронизировать `Dockerfile.orchestrator` (stage/prod) с реальным списком нужных для пилота коннекторов — риск 5.
- Задокументировать `ecdsa` CVE как known/accepted risk в сопроводительных материалах — риск 6.
- Исключить `deploy/stage/` (или ротировать секрет) из передаваемого среза репозитория — риск 7.
