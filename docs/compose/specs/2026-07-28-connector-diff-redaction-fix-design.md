# Connector Config Diff — Redact Unchanged Context Lines (B2)

> Реализует B2 из `docs/concepts/BAGFIX_PLAN.md`. Закрывает регрессию,
> оставшуюся открытой после P13
> (`docs/compose/specs/2026-07-27-connector-secrets-schema-design.md`) —
> `GET /connectors/{name}/config/diff` отдаёт секреты роли `viewer` через
> контекстные строки unified diff.

## [S1] Problem

`_DIFF_KV_RE` (`orchestrator/api/connectors.py:34`):

```python
_DIFF_KV_RE = re.compile(r"^([+-])(\s*)([A-Za-z_][A-Za-z0-9_]*):\s*(.*)$")
```

Группа 1 требует ровно `+` или `-`. В unified diff (`git diff`, вывод
`GitManager.diff_versions`, см. `orchestrator/core/history.py`) строки,
которые не менялись между двумя версиями, но попали в диапазон hunk'а
(контекст вокруг реально изменённых строк), начинаются с **пробела**, не
с `+`/`-`. Пример из ревью — правка `base_url`, соседнее поле `password`
не менялось:

```
@@ -1,4 +1,4 @@
 instances:
   x1:
-    base_url: https://a
+    base_url: https://b
     password: SUPERSECRET      ← контекстная строка (ведущий пробел)
```

`_DIFF_KV_RE.match(" password: SUPERSECRET")` не матчит (первый символ —
пробел, не входит в `[+-]`) → `_redact_diff()` (`connectors.py:124-139`)
пропускает строку как есть в `out_lines`, значение уходит в ответ
нередактированным. Роут — `_RO` (`connectors.py:592`), самая
низкопривилегированная роль `viewer` имеет доступ.

Затронуты обе стороны diff'а одинаково: если бы `password` был на стороне
`+` или `-` (реально менялся), regex сработал бы и замаскировал его —
баг специфичен именно к **неизменённым** hidden-полям, случайно попавшим
в контекст соседней правки. При стандартном контексте unified diff
(3 строки, дефолт git) вероятность задеть соседнее поле в реальном
`instances.<id>: {...}` блоке (обычно 3-8 полей) высокая на любой правке
не-hidden поля того же инстанса.

## [S2] Solution

Разрешить группе 1 матчить и пробел — контекстная строка тоже
`key: value`, просто с другим префиксным символом:

```python
_DIFF_KV_RE = re.compile(r"^([+\- ])(\s*)([A-Za-z_][A-Za-z0-9_]*):\s*(.*)$")
```

`_redact_diff()` не меняется структурно — уже переиспользует
`match.group(1)` как префикс при реконструкции строки
(`connectors.py:136`: `f"{match.group(1)}{match.group(2)}{match.group(3)}: {_MASK}"`),
значит захват пробела как группы 1 автоматически восстанавливает
корректный контекстный префикс (`" "`, не `"+"`/`"-"`) в отредактированном
выводе — правка одной строки, без изменений остального тела функции.

Единственный риск ложного срабатывания: строки `+++`/`---` (заголовки
diff-файлов, начинаются с трёх символов `+`/`-`) уже исключены явной
проверкой до вызова regex (`connectors.py:131-133`,
`if line.startswith("+++") or line.startswith("---")`) — не пересекается
с этим изменением, `_DIFF_KV_RE` не видит эти строки вообще.

Ложные срабатывания на "случайно похожих" контекстных строках вроде
` some_password_hint: not a real value` — та же эвристика, что уже
принята для `+`/`-` строк сегодня: если имя ключа буквально совпадает с
`HIDDEN_FIELDS`, маскируется, независимо от того, секрет там реально или
комментарий/строка-подсказка. Не хуже текущего поведения на `+`/`-`
строках — не новый класс риска.

## [S3] Regression check

`/config/history/{commit}` и `GET /config` используют отдельную функцию
`_redact_yaml()` (парсинг YAML целиком, не построчный regex) — не задеты
этим багом и не меняются этим фиксом. Только `/config/diff` строит вывод
построчным regex-парсингом текстового unified diff, потому что
`git diff` не даёт распарсенную структуру — эта асимметрия
(YAML-парсинг для snapshot'ов, regex для diff) была осознанным решением
P13 (`connector-secrets-schema-design.md` [S6]) и остаётся; фикс здесь
точечный, к самому regex, не к архитектуре.

## [S4] Testing Strategy

`tests/orchestrator/api/test_connectors.py`:

- **Новый** `test_config_diff_redacts_unchanged_hidden_field` —
  воспроизводит репортнутый баг ровно: сохранить конфиг с
  `password: SECRET1`, изменить только `base_url` (не трогая `password`),
  запросить `/config/diff` между двумя версиями → `password` в выводе
  замаскирован (`********`), несмотря на то что попал в diff только как
  контекстная строка. Этот тест падает на текущем коде (`SECRET1` виден в
  выводе) и проходит после [S2].
- **Регрессия** `test_config_diff_redacts_changed_hidden_field` (если
  такого теста ещё нет — добавить; если есть — убедиться, что он
  по-прежнему проходит): изменить `password` явно (`+`/`-` строки) →
  обе стороны (`-password: OLD`, `+password: NEW`) замаскированы.
- Тест на `viewer` роль явно (не только `admin`) — баг специфичен к
  самой низкопривилегированной read-роли, воспроизвести с её токеном/ролью.

## [S5] Success Criteria

- [ ] `password`/`api_key`/любое `HIDDEN_FIELDS`-поле никогда не
      появляется в ответе `/config/diff` в открытом виде — ни на `+`/`-`
      строке, ни на контекстной
- [ ] Факт изменения hidden-поля (какое поле, было ли `+`/`-`) остаётся
      видимым — маскируется только значение, не структура diff'а
- [ ] Regression-тест на уже покрытый случай (`+`/`-` hidden-поле) остаётся
      зелёным
- [ ] `docs/agents/security-patterns.md` обновлён вместе с этим фиксом
      (см. D1 — только после того, как фикс реально внедрён)
