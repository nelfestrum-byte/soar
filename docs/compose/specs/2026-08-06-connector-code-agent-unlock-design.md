# `PUT /connectors/{name}/code` возвращается роли `agent`; конфиг коннектора у неё забирается

> Отменяет решение B3
> (`docs/compose/specs/2026-07-28-connector-code-agent-lockdown-design.md`).
> Повод — фидбэк из боя: агент написал коннектор `elastic_trueconf` и не смог
> его сохранить. Проверка кода показала, что барьер B3 создаёт трение, но не
> держит: он обходится через `POST /connectors/{name}` + `POST /code/restore`,
> обе ручки роли `agent` разрешены.

## [S1] Problem

### (a) Барьер B3 обходится в два запроса

B3 запинил `PUT /connectors/{name}/code` на литеральный `admin`
(`orchestrator/api/connectors.py:520-523`), рассуждая так: `POST
/{name}/code/restore` может остаться на `_ADMIN`, потому что restore лишь
воспроизводит уже существующую в git версию, а «любая версия, где
`HIDDEN_FIELDS` был сужен, уже была бы записана только через `PUT` от
`admin`».

Посылка неверна. `create_connector` (`connectors.py:674-721`, роль `_ADMIN`,
т.е. агенту разрешена) пишет и коммитит `CONNECTOR_TEMPLATE`
(`connectors.py:50-56`), в котором `HIDDEN_FIELDS: ClassVar[set[str]] =
set()`. Это версия с пустым `HIDDEN_FIELDS`, попавшая в историю **не** через
`PUT` и **не** от `admin`. Отсюда:

1. `POST /connectors/x` — агент создаёт коннектор, первый коммит: шаблон,
   `HIDDEN_FIELDS` пуст.
2. `admin` пишет настоящий код с `HIDDEN_FIELDS = {"api_key"}` и заполняет
   конфиг.
3. `POST /connectors/x/code/restore` на коммит из шага 1 — агенту разрешено.
   `HIDDEN_FIELDS` снова пуст.
4. `GET /connectors/x/config` — `_hidden_fields_for` возвращает пустое
   множество, `_redact_yaml` не маскирует ничего, `api_key` открытым текстом.

То есть ровно та эксплуатация, которую B3 закрывал, осталась рабочей — сменив
`PUT` на `restore`. Ограничение легло на честный сценарий (агент пишет код
коннектора) и не легло на обход.

### (b) Редакция fail-open

`_hidden_fields_for` (`connectors.py:95-107`) возвращает пустое множество,
когда `.py` отсутствует, не парсится (`SyntaxError`) или не содержит классов.
Пустое множество на выходе неотличимо от «секретов нет», и `_redact_yaml`
(`connectors.py:110-125`) отдаёт конфиг **без маскировки**. Любой путь,
приводящий к нечитаемому или отсутствующему `.py` при живом `.yml`,
раскрывает секреты — включая `POST /transfer/export`, который пользуется той
же парой функций (`orchestrator/api/transfer.py:56-59`).

### (c) Запрет мешает работе, ради которой роль `agent` заведена

Написание коннектора — основной сценарий агента: он единственный, кто
объявляет `HIDDEN_FIELDS` осмысленно, потому что он же пишет `__init__` и
знает, какой параметр является credential. Системный промпт
(`orchestrator/prompts/system_prompt.md:108-119`) честно предлагает «опиши
изменение и попроси человека применить», но механизма passthrough в API нет —
ни черновика, ни `approve`. На практике оператор с admin-ключом руками
переносит многострочный Python через Swagger UI. Единственный review-gate в
системе сделан самым неэргономичным способом из доступных — и при этом,
согласно (a), не защищает.

### (d) Что при этом НЕ является проблемой

Прямого чтения секретов через конфиг у агента нет и не было: значения
`HIDDEN_FIELDS` маскируются `********` для **всех** ролей, включая `admin`
(`docs/agents/security-patterns.md`, секреты write-only). Ценность
`HIDDEN_FIELDS` — не в том, что агент не видит конфиг, а в том, что политика
редакции не может быть тихо снята.

## [S2] Solution

Три части, каждая бессмысленна без остальных.

### 1. Роли

Добавляется `_CONFIG_RO = ("viewer", "analyst", "service", "admin")` — `_RO`
без `agent`.

| Ручка | Было | Стало |
|---|---|---|
| `PUT /{name}/code` | `"admin"` | `*_ADMIN` |
| `GET /{name}/config` | `*_RO` | `*_CONFIG_RO` |
| `GET /{name}/config/history/{commit}` | `*_RO` | `*_CONFIG_RO` |
| `GET /{name}/config/diff` | `*_RO` | `*_CONFIG_RO` |
| `PUT /{name}/config` | `*_ADMIN` | `"admin"` |
| `POST /{name}/config/restore` | `*_ADMIN` | `"admin"` |

Разделение владения: **агент владеет кодом, человек — значениями конфига**.
Агент объявляет в коде, какие поля являются секретами, и сообщает оператору,
что заполнить; оператор заполняет. Агент не читает конфиг, поэтому и писать
его не может — `PUT` пишет файл целиком, слепая запись затирала бы значения,
которых агент не видит.

`GET /{name}/config/history` (список коммитов) остаётся на `_RO`: в нём нет
значений, а агенту полезно видеть, что конфиг заполнили. `GET /{name}/schema`
остаётся на `_RO` и становится штатным способом узнать имена полей и флаг
`hidden` без значений.

### 2. Редакция fails closed

`_hidden_fields_for` меняет тип на `set[str] | None`, где `None` = «политика
неизвестна» (нет файла, `SyntaxError`, нет классов). Пустое множество
сохраняет смысл «секретов нет» — шаблон объявляет `HIDDEN_FIELDS = set()`
явно, и это валидное объявление.

- `_redact_yaml(content, None)` — маскирует каждое скалярное значение под
  `instances.*`.
- `_redact_diff(diff, None)` — маскирует значение в каждой строке `key: value`.
- `save_connector_config` — ветка `if hidden:` обрабатывает и `None`.
- `transfer.py` получает то же поведение бесплатно, через общие функции.

Неизвестная политика больше не означает «показывай всё».

### 3. `HIDDEN_FIELDS` нельзя сузить не-админом

Это та самая альтернатива, которую B3 рассмотрел и отложил ([S3] в спеке B3:
«дороже, отдельная спека, если понадобится вернуть `agent` право
редактировать код коннекторов»). Понадобилось — делаем.

Новый хелпер `_assert_hidden_fields_not_narrowed(config, name, new_source,
user)`: старое множество берётся с диска через `_hidden_fields_for`, новое —
из ещё не записанного текста; при `user.role != "admin"` и `not new >= old`
→ `403`. Если старое `None` (текущий файл не парсится), не-admin получает
`403` — то же fail-closed.

Применяется во **всех трёх** путях записи кода коннектора, а не только в
`PUT`, — иначе повторяется ошибка B3:

- `save_connector_code` (`PUT /code`) — после `validate_connector_code`, до записи;
- `restore_connector_code` (`POST /code/restore`) — содержимое целевого
  коммита читается через `history.get_version` и проверяется до отката; это
  закрывает обход из [S1](a);
- `generate_connector` (`POST /generate`, `_ADMIN`) — при перезаписи
  существующего коннектора.

Для нового коннектора старое множество — пустое (шаблон от `POST`), любое
новое является его надмножеством: авторский сценарий агента не ломается.
Сужение остаётся возможным — но только человеком с ролью `admin`.

## [S3] Границы трека — что сознательно не чинится

У роли `agent` уже есть произвольное исполнение кода: она пишет код воркфлоу
(`orchestrator/api/workflows.py:279-282`, `_ADMIN`) и создаёт джобы
(`orchestrator/api/jobs.py`, `_RW`). В субпроцесс джоба монтируется срез
конфига с креды в открытом YAML (`build_scoped_config`,
`orchestrator/core/subprocess_runner.py:69-162`).
`ConnectorProxy.__getattr__` (`soar/connectors/_proxy.py:25-29`) возвращает
сырое значение для всего, что не callable, и для всего, что начинается с
`_` — то есть `conn.api_key` и `conn._instance` доступны коду воркфлоу
(вопреки утверждению в docstring того же файла). Логи джоба отдаются без
редакции (`orchestrator/api/logs.py:13-26`).

Следовательно `print(conn.api_key)` в воркфлоу + `GET /logs/{id}` выдаёт
креды **уже сегодня**, независимо от этого трека, и данный трек этого не
меняет ни в одну сторону.

Из этого следует формулировка, которая должна быть записана в
`known-limitations.md` без смягчения: после этого трека «агент не видит
креды» — свойство API-поверхности и целостности политики редакции, **не**
обеспеченная граница против враждебного агента. Граница требует работы в
рантайме контента и вынесена в
`docs/compose/specs/2026-08-06-connector-secret-runtime-boundary-design.md`.

Причина не делать это здесь: правка `ConnectorProxy` меняет контракт рантайма
контента (воркфлоу, читающие атрибуты коннектора, перестанут работать) и
требует своей миграции — смешивать её с RBAC-правкой значит получить
нереверсируемый одним откатом коммит.

## [S4] Testing Strategy

`tests/orchestrator/api/test_agent_role_rbac.py`:

- `test_agent_cannot_write_connector_code` → переворачивается в
  `test_agent_can_write_connector_code` (200): тест кодирует ровно то
  решение, которое отменяется.
- Новые `403` для `agent`: `GET /config`, `GET /config/history/{commit}`,
  `GET /config/diff`, `PUT /config`, `POST /config/restore`.
- Новые `200` для `agent`: `GET /config/history`, `GET /{name}/schema` —
  фиксируют, что осталось доступным.
- `test_agent_can_restore_connector_code` — приводится к версии, где откат не
  сужает `HIDDEN_FIELDS` (restore сам по себе агенту остаётся).

Новый `tests/orchestrator/api/test_connector_hidden_fields_integrity.py`:

- агент пишет код без `HIDDEN_FIELDS` поверх кода с ними → `403`, файл на
  диске не изменился;
- агент расширяет `HIDDEN_FIELDS` → `200`; `admin` сужает → `200`;
- **регрессия на [S1](a)**: `POST /connectors/x` → `admin` `PUT /code` с
  `HIDDEN_FIELDS={"api_key"}` → агент `restore` на шаблонный коммит → `403`,
  и последующий `GET /config` под `admin` по-прежнему маскирует значение;
- fail-closed: коннектор со сломанным `.py` → `GET /config` под `admin`
  маскирует всё, а не отдаёт plaintext.

Существующие тесты редакции в `test_connectors_api.py` должны остаться
зелёными без правок — [S2](2) расширяет поведение только на ветку `None`.

## [S5] Success Criteria

- [ ] `PUT /connectors/{name}/code` от роли `agent` — `200`; сценарий из
      фидбэка (создать коннектор, записать код с `HIDDEN_FIELDS`) проходит
      целиком без admin-ключа
- [ ] `agent` получает `403` на чтение и запись конфига коннектора; `schema`
      и список коммитов конфига ему остаются
- [ ] `HIDDEN_FIELDS` невозможно сузить ролью `agent` ни через `PUT /code`,
      ни через `POST /code/restore`, ни через `POST /generate`
- [ ] Нечитаемый/отсутствующий `.py` больше не приводит к выдаче конфига без
      маскировки — ни в `GET /config`, ни в `/config/diff`, ни в `/transfer/export`
- [ ] `system_prompt.md` §4, `security-patterns.md`, `api-reference.md`
      описывают новое поведение; `known-limitations.md` содержит запись из
      [S3] без смягчения формулировки
